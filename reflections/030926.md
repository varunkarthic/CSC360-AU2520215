# Reflection - 3 September 2026

## Topics Discussed

- Generating an ASCII tree using Java text output
- Finding common elements between two lists and drawing arrows
- Creating a custom JavaFX splash screen with FXML

## Reflection

This class extended the previous discussion about trees and connections by showing how the same ideas can be represented in different media. The ASCII-tree program does not use a canvas, but it still has to solve a layout problem. Spaces, rows, columns, and branch characters take the place of x and y coordinates. This helped me understand that alignment is a general graphics problem, even when the output is only text in a terminal.

The two-list arrow exercise demonstrated the importance of separating data processing from rendering. The program first needs to determine which elements are common and where those elements occur in each list. Only after the relationships are known should it draw the list labels and arrows. This approach makes the drawing logic simpler and also makes it easier to test the matching behavior independently.

I found the question of duplicate values especially important. A simple comparison may work when every value is unique, but repeated values require an explicit decision about which items should be connected. This reminded me that a visual result depends on a precise interpretation of the underlying data, not only on the drawing commands.

The FXML splash-screen exercise introduced a different kind of separation. FXML describes the interface structure, the controller describes user-interface behavior, and the application class manages the JavaFX stages. This is cleaner than creating every control manually in one large method. I also learned why background work matters: a splash screen should remain responsive while the application is loading.

Overall, the class connected console output, algorithmic relationships, and desktop user-interface design. The common idea across all three exercises was to model the information first and choose a suitable visual representation afterward. That principle should make future graphics programs easier to reason about, test, and maintain.
