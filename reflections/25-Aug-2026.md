## Topics Discussed

- The purpose and structure of the `pom.xml` file in Maven
- Swing thread safety and the role of the Event Dispatch Thread
- The difference between threads and processes
- How long-running work can freeze a graphical user interface
- Using a background thread while keeping the GUI thread responsive

## Reflection

Learning about `pom.xml` helped me understand how Maven organises a Java project. Instead of managing libraries and build settings manually, Maven can use the Project Object Model to identify the project, download dependencies, compile the source code, and run tests.

The discussion of Swing made me realise that a graphical interface is not automatically safe when several parts of a program use it. Swing components should be handled on the Event Dispatch Thread, and the `Graphics` object should only be used during the painting operation. This showed me that thread safety is part of the design of a GUI, not just a technical detail.

Comparing threads and processes clarified why threads are useful for applications that need to do several tasks at once. Processes have separate memory and stronger isolation, while threads share the memory of their process and can communicate more easily. However, shared memory also means that threads must be coordinated carefully.

I also learned why a GUI can appear to freeze when the main interface thread performs every task. A long calculation, file operation, or network request can stop the interface from responding to events and repainting the window. Moving that work to a background thread allows the Event Dispatch Thread to continue handling the GUI.

Overall, the main lesson was that a responsive Swing application needs a clear separation between interface work and background work. The EDT should manage Swing components and painting, while a worker thread handles tasks that may take time. This gives me a better foundation for improving the moving triangle and square programs without making their interfaces unresponsive.
