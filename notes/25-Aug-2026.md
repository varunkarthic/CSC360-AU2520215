# Maven Project Structure and Threading in Java Swing
*Tuesday, 25 August 2026*

## POM.xml in Maven

Maven uses the `pom.xml` file, where POM means **Project Object Model**, to describe and manage a Java project. It contains project information such as the group ID, artifact ID, version, dependencies, build plugins, and Java compiler settings.

The group ID usually identifies the organisation or project namespace, while the artifact ID identifies the application or library. Together with the version, these values identify the project when Maven builds or publishes it.

Dependencies are external libraries required by the project. Maven reads the dependency declarations in `pom.xml`, downloads the required libraries, and makes them available to the source code and tests. This is more reliable than manually copying JAR files into the project.

A Maven project commonly separates its files into these directories:

```text
src/main/java       application source code
src/main/resources  application resources
src/test/java       test source code
src/test/resources  test resources
target              generated build output
```

The `target` directory contains compiled classes and other generated files. Since it can be recreated by Maven, it is normally excluded from version control with `.gitignore`.

## Swing and Thread Safety

Swing is not thread-safe. This means that Swing components and their state should not generally be changed from multiple threads at the same time. Concurrent changes could produce inconsistent state, visual errors, or unpredictable behaviour.

Swing therefore uses the **Event Dispatch Thread (EDT)** to process user-interface events and update components. Creating or modifying Swing components should normally happen on the EDT, for example by using `SwingUtilities.invokeLater`:

```java
SwingUtilities.invokeLater(() -> {
    JFrame frame = new JFrame("Example");
    frame.setVisible(true);
});
```

Painting is also performed by Swing on the EDT. The `Graphics` object passed to `paintComponent` belongs to that painting operation and should be used only inside the painting method. It should not be stored and reused by another thread. A background thread should update application data and then request a repaint with `repaint()` rather than drawing directly.

For example, the safe division of responsibility is:

```text
EDT              creates components, handles events, and paints
worker thread    performs long-running calculations or I/O
shared state     is updated using an appropriate thread-safe design
```

## Threads and Processes

A **process** is a running program with its own memory space and system resources. Processes are isolated from one another, so communication between them usually requires mechanisms such as pipes, sockets, or files.

A **thread** is a unit of execution inside a process. Threads in the same process share memory and resources, which makes communication easier but also creates the risk of race conditions when multiple threads access the same data.

The main differences are:

| Feature | Process | Thread |
| --- | --- | --- |
| Memory | Separate memory space | Shares the process memory |
| Communication | More expensive | Usually easier and faster |
| Isolation | Stronger isolation | Less isolation |
| Creation cost | Generally higher | Generally lower |
| Failure impact | Usually limited to that process | Can affect the whole process |

A Java Swing application is normally one process containing several threads, including the EDT and any worker threads created by the application.

## Preventing a Frozen GUI

If the EDT performs every task, a long-running operation can prevent it from processing input, repaint requests, and window events. The result is a GUI that appears frozen or unresponsive.

For example, placing a large loop, file operation, network request, or complex calculation directly inside an event handler blocks the EDT until the operation finishes. The window cannot repaint properly during that time.

The solution is to keep the EDT responsive and move long-running work to a background thread. Once the work is complete, the worker can safely request a UI update on the EDT. `SwingWorker` is a standard Swing utility for this pattern:

```java
SwingWorker<String, Void> worker = new SwingWorker<>() {
    @Override
    protected String doInBackground() throws Exception {
        return performLongTask();
    }

    @Override
    protected void done() {
        // This method runs on the EDT and can update Swing components.
        resultLabel.setText(getResultSafely());
    }
};

worker.execute();
```

The important design is not simply to create threads, but to assign work to the correct thread. The EDT should remain available for the interface, while background work should handle tasks that may take noticeable time. Therefore, a responsive application generally needs at least the EDT and a worker of some kind when it performs lengthy tasks.

## Main Lesson

This class connected project organisation with program execution. Maven's `pom.xml` manages how a project is built, while Swing's threading model determines how the running application remains safe and responsive. Understanding the difference between UI work and background work is essential when building graphical Java programs.
